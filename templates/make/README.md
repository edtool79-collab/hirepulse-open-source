# שלושה מתכוני Make להגדרה ידנית

אלה מתכונים עם כתובת API, קלט ותקרת עלות; הם אינם קובצי Blueprint לייבוא.
לא הומצאו מזהים פנימיים של מודולים. אין כאן התחברות לחשבון, תזמון פעיל או הרצה בתשלום.

| מתכון | תזמון מוצע | קלט מרבי | תקרת חיוב לכל הרצה |
| --- | --- | --- | --- |
| competitor-new-ads-weekly | שני ב־08:00, שעון ישראל | 3 דומיינים | $1 |
| ats-new-jobs-daily | כל יום ב־08:00, שעון ישראל | 3 חברות | $1 |
| company-intent-weekly-enrichment | שני ב־08:00, שעון ישראל | 5 דומיינים | $1 |

להגדרה ב־Make: בוחרים חיבור Apify פרטי, מרכזים את הרשימה כולה לחבילה אחת, ואז משתמשים במודול Apify / Make an API Call.
מעתיקים את ה־method, הנתיב, query וה־body מהמתכון. יש להתאים את שדה הכתובת לממשק המודול בפועל; אין לייבא את קובץ המתכון כ־Blueprint.
משאירים את הסוד בחיבור הפרטי בלבד. `YOUR_` הוא מציין מקום שצריך להחליף לפני הפעלה.
יש לעצור על רשימה ריקה, כפילויות או חריגה מגודל הרשימה; אין לשים את הקריאה בתשלום אחרי Iterator שמוציא פריט לכל דומיין.
על שגיאה או timeout עוצרים ובודקים את ההרצה הקיימת ב־Apify Console. אין ניסיון אוטומטי חוזר.
ממפים את הפלט לפי ההוראות בכל מתכון ורק אחרי בדיקת המיפוי קובעים תזמון.

מבנה Blueprint תקין לייבוא ותאימות לגרסת Make אינם בטוחים בלי ייצוא אמיתי או בדיקה במערכת. הם לא נבדקו במסגרת הזאת.
[תיעוד החיבור הרשמי של Apify](https://docs.apify.com/integrations/make) מתאר גם את מודול הקריאה ל־API.
[תיעוד Make](https://help.make.com/blueprints) מתאר ייצוא וייבוא Blueprint וחיבורי חשבונות אחרי ייבוא.
